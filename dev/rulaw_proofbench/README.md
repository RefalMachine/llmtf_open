# RuLaw-ProofBench: два этапа

**Подготовка входных данных** и **построение датасета** выполняются отдельно.
Подготовка заканчивается принятым пакетом норм `input-package.json`.
Основной алгоритм читает этот пакет, создаёт правила и вопросы и проверяет
их соответствие переданным нормам. История редакций остаётся в подготовке.

Новая сборка завершена: **194 test + 5 few-shot**, без технических ошибок.
Она опубликована в [RefalMachine/RuLaw-ProofBench](https://huggingface.co/datasets/RefalMachine/RuLaw-ProofBench/tree/6e753317f0a7d17c92ca243c85aa0c2ef7a7cecc)
и закреплена в загрузчике LLMTF. На HF находятся только README и четыре Parquet,
без столбца `as_of`. Проверки и исторические результаты — в [отчёте](DEVELOPMENT_REPORT.md).

## Окружение

Python 3.10+, PyYAML 6.0.2; GPU не нужен. В отдельном окружении:

```bash
python3 -m pip install -r dev/rulaw_proofbench/requirements.txt
```

Для команд с API задайте ключ скрытым вводом:

```bash
read -rs -p 'OpenRouter API key: ' OPENROUTER_API_KEY
export OPENROUTER_API_KEY
```

Если нужен прокси, задайте `HTTPS_PROXY` в окружении.
Ключ не помещается в конфигурацию или артефакты.

## Этап 1. Подготовить входной пакет

Можно подготовить нормы вручную либо выполнить отдельную процедуру `prepare`.
Пакет содержит конкретные статьи и зависимости, происхождение и хеши текстов,
проверяемое следствие, split, дату и ограничения применения.
Принятие означает решение подготовителя, а не юридическую экспертную гарантию.

Для автоматизированной подготовки используются 38 сохранённых файлов
из `dev/rulaw_artifacts/inputs/`. Они нужны только этому этапу.
Состав и переносимый архив описаны в [INPUTS.md](INPUTS.md).

```bash
python3 -m dev.rulaw_proofbench.builder check-inputs
python3 -m dev.rulaw_proofbench.builder prepare \
  --config dev/rulaw_proofbench/configs/prepare-release.json \
  --output dev/rulaw_artifacts/prepared-release-v1 \
  --workers 4
```

Подготовка рассматривает весь явно заданный пул: 94 тестовые статьи и
8 кандидатов для демонстраций. Здесь нет остановки по квоте вопросов:
вопросы ещё не строятся. Часть статей может быть отклонена. Подготовка
имеет собственные запросы, расходы и `report.json`; эта стоимость не входит
в отчёт последующей сборки.

Успешный результат — `prepared-release-v1/input-package.json`.
Подробные документы проверки, включая `source-basis.json`, остаются
в каталоге подготовки и основному алгоритму не передаются.

### Ручная подготовка

Формат показан в [configs/manual-example.json](configs/manual-example.json).
В нём **вымышленная норма**, он предназначен только для знакомства с форматом.
Для рабочего пакета нужно вписать реальные принятые нормы и ограничения,
указать автора принятия и вычислить хеши документов/фрагментов.

Проверить структуру и зафиксировать принятый вручную JSON можно без ключа и сети:

```bash
python3 -m dev.rulaw_proofbench.builder seal-inputs \
  --inputs my-input-draft.json --output my-input-package-v1.json
python3 -m dev.rulaw_proofbench.builder check-package \
  --inputs my-input-package-v1.json
```

`seal-inputs` не проводит юридическую проверку и не принимает входы за автора.
Он требует явного `status: accepted` и сведений `acceptance`,
проверяет структуру и хеши, затем фиксирует контрольную сумму пакета.
Для изменения уже сохранённого пакета нужен новый путь/версия.

## Этап 2. Построить датасет

```bash
bash dev/rulaw_proofbench/build.sh \
  --inputs dev/rulaw_artifacts/prepared-release-v1/input-package.json \
  --output dev/rulaw_artifacts/runs/full-300-v1 \
  --workers 4
```

`--inputs` обязателен. Сборка не запускает подготовку автоматически,
не читает исходный каталог из 38 файлов и не скачивает нормативные документы.
Ей достаточно принятого JSON-пакета, конфига сборки и API.
Параметры полной сборки — в `configs/release.json`; поля подготовки туда
передавать нельзя. При недостаточности норм статья получает `input_gap`
с причиной возврата к подготовке, пакет остаётся неизменным.

В терминале обновляется полоса по статьям и названия текущих этапов;
при перенаправлении stderr сохраняются обычные строки.
`--workers 1` — последовательный режим, `--quiet` скрывает прогресс.
Подготовка считает принятые статьи, сборка — принятые вопросы.
Процент обработанных статей не является прогнозом времени.

Сборка держит до `workers` выполняющихся статей и резерв задач в пределах
окна до `2 × workers`. Освободившийся поток берёт задачу из резерва,
пока результаты добавляются в исходном порядке. При остатке квоты не больше
`workers × вопросов_на_статью` окно уменьшается до `workers`.
Это уменьшает простой за медленной статьёй; уже поставленные в очередь
статьи могут завершиться сверх квоты и также требуют оплаты.

## Короткий пилот

Используйте `configs/prepare-pilot.json` для подготовки трёх статей СК.
Затем передайте полученный пакет в сборку с `--config configs/pilot.json`
(полный путь от корня: `dev/rulaw_proofbench/configs/pilot.json`).
Цель пилота — 8 test + 1 few-shot; это не гарантия принятия всех карточек.

## Проверка и повторение

Обе фазы имеют собственный каталог, снимок кода/YAML и журнал API.
Для любого завершённого каталога:

```bash
python3 -m dev.rulaw_proofbench.builder verify --output ПУТЬ_К_КАТАЛОГУ
python3 -m dev.rulaw_proofbench.builder replay --output ПУТЬ_К_КАТАЛОГУ
python3 -m dev.rulaw_proofbench.builder cost --output ПУТЬ_К_КАТАЛОГУ
```

Replay выбирает фазу из манифеста и запускает сохранённый код в копии без сети
и ключа, сравнивая хеши артефактов. Для старого YAML команда `verify`
принимает `--expected-bundle` с сохранённой версией.

Выход сборки: `test.jsonl`, `train.jsonl`, `report.json`, материалы
`stages/` и точная копия `input-package.json`. Каждая запись содержит
хеш пакета и своей входной статьи. Итоговое разделение test/few-shot учитывает
все нормативные зависимости принятых вопросов.

Коды выхода: **0** — подготовка завершена / объём сборки достигнут;
**2** — недобор; **1** — техническая ошибка. `prepared` не означает 300+5
готовых вопросов, а `accepted` в пакете не означает экспертной юридической оценки.
Долларовых блокировок нет; неизвестная цена не заменяется нулём.
Повторный запуск в том же каталоге требует тех же входов и кода.
HTTP 429 повторяется до четырёх раз с паузами 30, 60, 120 и 240 секунд.
Если `Retry-After` требует более долгого ожидания, используется оно.
В режиме `--retry-failed` обрывы чтения ответа, другие ошибки транспорта
и некорректный JSON ответа также повторяются с этими паузами.
Без флага они записываются как ошибки статьи. Другие HTTP-статусы,
кроме 429, автоматически не повторяются.

### Продолжить после ошибок API

После завершения текущего процесса используйте **тот же каталог и настройки**:

```bash
bash dev/rulaw_proofbench/build.sh \
  --config dev/rulaw_proofbench/configs/release.json \
  --inputs dev/rulaw_artifacts/prepared-release-v1/input-package.json \
  --output dev/rulaw_artifacts/runs/full-300-v1 \
  --workers 4 --retry-failed
```

Подставьте пути исходного запуска. Команда использует существующий принятый
пакет и продолжает построение датасета, не выполняя подготовку повторно.

Флаг поддерживают и команды `prepare`/`build`. Успешные ответы берутся из кеша
без повторной оплаты. Заново отправляются сохранённые запросы без API-ответа
(HTTP-ошибка, ошибка транспорта или прерывание); ещё не выполнявшиеся запросы
также выполняются. Содержательные отказы модели не пересматриваются. Локальные
шаги и итоговые файлы восстанавливаются из сохранённых ответов.

Неудачные попытки сохраняются в `failed_attempts`, их неизвестная стоимость
не заменяется нулём. Флаг также разрешает переход с известной версии построителя
до этого исправления: прежний снимок сохраняется в `implementation-history`.
Промпты, входы, модели, конфигурация и логика построения должны остаться прежними.
Работающий каталог защищён блокировкой: два процесса одновременно его не обрабатывают.

### Продолжить через свою API-прослойку

Остановите прежнюю сборку через Ctrl+C и запустите в том же каталоге:

```bash
export RULAW_API_BASE=http://127.0.0.1:8080/v1
export RULAW_API_PROFILE=generic
bash dev/rulaw_proofbench/build.sh \
  --config dev/rulaw_proofbench/configs/release.json \
  --inputs dev/rulaw_artifacts/prepared-release-v1/input-package.json \
  --output dev/rulaw_artifacts/runs/full-300-v1 \
  --workers 4 --retry-failed
```

Перед запуском передайте `RULAW_API_KEY` через окружение или механизм секретов.
Локальный API вызывается напрямую, без прокси. Адрес должен указывать
на базу OpenAI-совместимого API, без `/chat/completions` в конце.
Для обычного API (`RULAW_API_PROFILE=generic`) reasoning, лимит ответа и
JSON-формат сохраняются; поля OpenRouter `provider` и `plugins` не передаются.

Для вашей подписочной прослойки на `localhost:8080` скрипт по умолчанию
выбирает `RULAW_API_PROFILE=subscription`. Этот профиль передаёт
`reasoning_effort=high` вместо вложенного `reasoning`, исключает неподдерживаемые
`max_tokens` и `response_format`, а также снимает префикс `openai/` с имён моделей.
Ограничение ответа в 12 000 токенов здесь не применяется: длину определяет
подписочный маршрут. JSON запрашивается теми же промптами и проверяется локально;
прежняя одна попытка исправления некорректного JSON сохраняется. Это изменение
транспортного протокола, а не доказательство идентичности двух сервисов.
Для другого адреса адаптера явно задайте `RULAW_API_PROFILE=subscription`.

Перед сборкой скрипт проверяет токен и получает каталог через `/models`.
Ошибка авторизации или получения каталога останавливает запуск до обработки
статей. Отсутствие явно выбранной модели в каталоге выводится в
`models_not_listed`, но не блокирует сборку: прямой запрос к `gpt-6.1-sol`
прошёл, хотя каталог её не перечисляет. Проверка каталога не выполняет
генерацию и не гарантирует доступность моделей или соблюдение квот подписки.

Успешные ответы сохраняются побайтно и повторно не отправляются. Новый адрес
используется для ошибочных и ещё не выполненных запросов; в журнале сохраняются
фактический endpoint и отправленный запрос. Смена транспорта не требует править
release-конфиг. Стоимость, которую прослойка не сообщает, остаётся неизвестной.

В generic-профиле передаются прежние имена `openai/gpt-6.1-sol` и `openai/gpt-6-astra`;
в subscription-профиле — `gpt-6.1-sol` и `gpt-6-astra`.
Если API использует другие имена, задайте `RULAW_MODEL` для основной модели
и `RULAW_REVIEW_MODEL` для разбора разногласий. Эти переменные применяются
только к новым сетевым запросам. Успешный кеш сохраняется, поэтому смена самой
модели создаёт смешанную сборку; фактические имена отражаются в журнале и `verify`.
Имена и поддержку параметров нужно проверить у вашей прослойки.
