# Входные документы и пул статей

## Вход основного алгоритма: один принятый пакет

Команда `build` получает **один файл `input-package.json`**, а не каталог
из 38 исходных файлов. В пакете уже зафиксированы:

- дата среза и способ приёмки;
- акт, его конкретная версия (URL и SHA-256), статья и принадлежность к test/train;
- точные тексты основной нормы и необходимых зависимых норм, с хешами;
- проверяемое следствие, область применения, временные ограничения и допущения.

Статьи зависимых актов здесь нужны только тогда, когда без них нельзя решить
выбранный вопрос. Например, переходное положение, непосредственно меняющее
применимость нормы, нужно включить как нормативный фрагмент. История изменений,
использованная только для подтверждения редакции, остаётся в отчёте подготовки.

Пакет можно подготовить вручную и зафиксировать командой `seal-inputs`, либо
получить командой `prepare`. Формат показан в
[учебном примере](configs/manual-example.json), команды — в [README](README.md).
Пример использует вымышленную норму и не является источником юридических вопросов.
`check-package` проверяет структуру и хеши, но не юридическую правильность приёмки.

Основной алгоритм не пересматривает историю редакции. Он проверяет, что правила
и вопросы соответствуют принятым нормам, области и времени. Если норм не хватает,
статья получает `input_gap`: входы нужно дополнить на этапе подготовки и создать
новую версию пакета. Автоматической дозагрузки в `build` нет.

## Материалы автоматизированной подготовки: 38 файлов

Каталог материалов подготовки содержит **38 файлов официального портала pravo.gov.ru**.
Это нормативные тексты и документы для проверки их редакции.
Готовые вопросы, исторические правила, ответы моделей и результаты старого
корпуса во входной пакет не входят.

Дата, относительно которой проверяется применимость выбранного положения, —
**1 января 2025 года**. Это заданный срез исследования, а не утверждение
о действующем сегодня праве. Номер `rdk` в URL — идентификатор версии портала;
он сам по себе не устанавливает дату вступления нормы в силу.

- **4 основных текста:** ТК, СК, часть первая ГК и 59-ФЗ. Из них извлекаются статьи.
- **4 сравнительных текста:** другие сохранённые редакции тех же актов.
  Сопоставляется конкретная статья, а не только заголовок документа.
- **4 перечня редакций:** показывают последовательность изменений.
  В этих страницах нельзя искать текст статьи закона.
- **5 карточек опубликования:** четыре основных акта и 125-ФЗ 2017 года.
  Они дополняют сведения об официальной публикации.
- **19 текстов поправок:** позволяют проверить, что изменилось и когда.
  Части крупных документов передаются по явным номерам статей из конфига.
- **2 общих документа:** 5-ФЗ об опубликовании и 52-ФЗ о введении части первой ГК.

На этапе `prepare` сохраняется отдельный `source-basis.json`: в нём видны
именно те тексты, по которым принято решение о редакции и зависимостях.
Страница с перечнем изменений и карточка публикации не заменяют нормативный текст.

## Где лежит пакет

Рабочий каталог: `dev/rulaw_artifacts/inputs/`.
Переносимый архив: `dev/rulaw_artifacts/official-inputs-2026-10-06.tar.gz`
(около 1,2 MiB). SHA-256 архива:

```text
c057477b49befb07bc1a29f002e4e6b4fd76c30c1beedfacefdf47e1590d7849
```

Пакет собран из локальных сохранённых официальных документов, использованных
при разработке; происхождение и прежние журналы сохранены в архиве из
[отчёта](DEVELOPMENT_REPORT.md). В эту сессию перечисленные URL заново не скачивались.
Проверены исходные хеши, повторное извлечение текста, наличие запрошенных статей
и статей для сравнения. Новых LLM-правил в пакете нет.

Полные SHA-256 исходных байтов и извлечённого текста, URL, размеры и заголовки
даны в [source_manifest.json](source_manifest.json).
`check-inputs` проверяет каждый используемый файл до платных запросов.
В Git хранится манифест; архив нужно переносить отдельно.

```bash
mkdir -p dev/rulaw_artifacts
tar -xzf dev/rulaw_artifacts/official-inputs-2026-10-06.tar.gz -C dev/rulaw_artifacts
python3 -m dev.rulaw_proofbench.builder check-inputs
```

## Из каких статей будут строиться вопросы

Пул подготовки фиксирован в [configs/prepare-release.json](configs/prepare-release.json):
**94 кандидата для test** и 8 для демонстраций. Подготовка рассматривает весь пул;
принятый пакет содержит прошедшие её статьи. Основной алгоритм использует
[configs/release.json](configs/release.json): не более десяти вопросов на статью.
Квоты 90/90/80/40 — явная
рабочая конфигурация этой сборки; они не были параметрами исторического пилота.
Порядок внутри каждого пула фиксирован и служит порядком отбора после проверок.

Для пяти демонстраций выделен отдельный пул из восьми статей с запасом:
**СК 56, 32, 60; ТК 115, 267, 185; ГК 20, 52**, именно в таком порядке.
При построении датасета с каждой принятой статьи берётся один вопрос; после пяти принятых статей
новые кандидаты не запускаются. Три дополнительных положения — резерв.
Случаи, уже запущенные параллельно сверх квоты, остаются в журналах.

Демонстрации формируются раньше test. Если тестовый вопрос использует норму
или зависимую статью, уже использованную в принятой демонстрации,
вся соответствующая тестовая карточка отклоняется. Редакции одного акта
на портале сопоставляются по `nd`, чтобы другой URL той же статьи не обходил
проверку разделения. Для дополнительно загруженных документов с другими
идентификаторами автоматическое установление юридической тождественности
не реализовано; их состав нужно проверить при приёмке.

## Что ещё нельзя считать доказанным

Запас из 94 статей не гарантирует 300 вопросов. Сложная статья может не пройти
сопоставление правил, дать мало разных сочетаний или потребовать недостающий
источник. В прежнем YAML-пилоте ГК 28 была отклонена из-за недостаточного
подтверждения редакции; в новый пакет добавлена карточка опубликования ГК,
но её достаточность для этой статьи ещё должна установить подготовка входов.

Для расширенного пула подтверждения редакций не объявлены заранее успешными.
Команда `prepare` проверяет их по каждой статье и допускает ограниченное число
запросов дополнительных официальных документов. Команда `build` использует
только уже принятые фрагменты. Неразрешённые вопросы на этапе подготовки
дают отказ, их причины сохраняются. Временная применимость и толкование норм
затем требуют содержательной проверки автором нового корпуса.
