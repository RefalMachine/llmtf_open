Суть фреймворка (краткая)

> Исторический development design record. Актуальный контракт находится в
> `../docs/`.
llmtf_open — фреймворк для оценки LLM на русскоязычных NLP-задачах. Ядро llmtf/:
- base.py — ABC Task и LLM, базовый класс SimpleFewShotHFTask для задач.
- evaluator.py — Evaluator: строит messages через task.load_dataset, зовёт у модели generate_batch / calculate_tokens_proba_batch / calculate_logsoftmax_batch, агрегирует метрики, пишет per-sample и total-логи.
- model.py (2030 строк, 8 классов) — бэкенды моделей: HFModel, VLLMModel, ApiVLLMModel и их *Reasoning варианты (6 backend-классов), плюс базовый миксин ReasoningModel и родитель LocalHostedLLM для локальных бэкендов (HF+vLLM). Жёстко сцеплены в одном файле, миксин ReasoningModel с MRO-хаками.
- tasks/ — конкретные задачи; регистрируются в TASK_REGISTRY в tasks/__init__.py.
Три способа прогона:
1. HF backend (evaluate_model.py без --vllm) — transformers.generate.
2. vLLM backend (--vllm) — локальный vLLM LLM.generate.
3. API backend (evaluate_model_api.py) — запросы к OpenAI-compatible vLLM серверу.
Два метода оценки: generate/calculate_tokens_proba (через Evaluator.evaluate) и PPL через calculate_logsoftmax (через Evaluator.evaluate_ppl, на сегодня реально работает только на HF).
3. Название: Reasoning как MODE инстанса — ModelKind + ReasoningStrategy (ликвидация *Reasoning подклассов)
Зачем. Reasoning-модели (Qwen3-think-стиль) сегодня — отдельные классы (*Reasoning), генерирующие reasoning-блок в два прохода: сначала до токена |THINK_CLOSE| идёт reasoning, затем continuation. Маркеры |THINK_OPEN| / |THINK_CLOSE| захардкожены в коде (model.py:78 stop-strings = [|THINK_CLOSE|]; get_end_thinking_token_id для HF/VLLM/API три разных реализации) — нерасширяемо. Variable shadowing for messages in messages_batch после цикла — хрупко. ВАЖНО: единый two-pass алгоритм работает на всех трёх backend'ах единообразно — API-бэкенд эмулирует его через server-side `max_tokens` (reasoning budget) + `stop` (строка |THINK_CLOSE|) + `stop_token_ids` (см. ApiVLLMModel.generate, model.py:434-440), повторно вызывая /v1/chat/completions для continuation. Никакого native-режима через `reasoning_content` НЕ предполагается — эмуляция stop-токенами даёт идентичную семантику HF/vLLM и сохраняет контроль truncation (reasoning_truncing_prompt) в руках фреймворка.

КЛЮЧЕВОЙ ПЕРЕХОД: отказываемся от подклассов *Reasoning как отдельных классов с логикой. Reasoning — это MODE инстанса, а не отдельный backend-тип. Сегодняшние подклассы — boilerplate forwarding (5 дублирующих методов на класс × 3 класса = ~15 методов-пустышек + 3 backend-specific `get_end_thinking_token_id`), вся двухпроходная алгоритмика уже определена один раз в ReasoningModel (model.py:123). Переносим её в composition-объект ReasoningStrategy и зашиваем в ядро backend-классов через свойство self._reasoning_kind.

Описание. В llmtf/models/reasoning.py:

- ModelKind (enum): `plain | reasoning | hybrid`. Свойство инстанса, выставляется в from_pretrained.
  - `plain` — модель не умеет reasoning (нет think-токена). one-pass всегда. `enable_thinking=True` → logger.warning + one-pass fallback (сегодня no-op).
  - `reasoning` — модель обязана reasoning (always two-pass). `enable_thinking=False` → error с понятным сообщением (логическая ошибка: модель должна thinking, но флаг запрещён).
  - `hybrid` — модель может reasoning включаемо (Qwen3-think стиль, today's default для всех reasoning-моделей). two-pass при `enable_thinking=True`, one-pass при `enable_thinking=False`. СЕГОДНЯ все прогоны `evaluate_model.py:41` всегда инстанцируют `HFModelReasoning`/`VLLMModelReasoning` (даже для instruct/base), `enable_thinking` flag выбирает режим — то есть de-facto `hybrid` и есть сегодняшний default. После рефактора auto-detect возвращает `hybrid` для моделей с think-токеном (поведение reasoning-моделей сохранено) и `plain` для остальных (поведение instruct/base, гнавшихся сегодня через `*Reasoning` + `enable_thinking=False`, сохранено — one-pass идентичен today's one-pass). CLI поведение пользователя **не меняется** (argc / argv пользователя те же, изменения только во внутренних импортах и инстанциации — см. CLI миграцию).

- ReasoningFormat (dataclass):
@dataclass
class ReasoningFormat:
    think_close: str = '|THINK_CLOSE|'        # закрывающий маркер reasoning-блока (используется как stop-string)
    truncation_prompt: str = '\n…the rest of the reasoning chain is hidden due to limit on the length of the thoughts.\n'
    end_thinking_token_id: Optional[int] = None  # backend-specific override; если None — берётся из токенайзера
Дефолты — Qwen3 (think_close = |THINK_CLOSE|). Любая reasoning-модель может подать свой ReasoningFormat через from_pretrained(..., reasoning_format=...). Это не обобщение на новые форматы (Qwen3-think остаётся единым форматом), а лишь вынос закрывающего токена и truncation-prompt в конфиг с qwen-дефолтами. (Открывающий маркер в текущем коде отдельно не нужен — reasoning стартует сразу после assistant-prompt, без явного open-токена в stop-условиях.)

- ReasoningStrategy (композируемый объект, не миксин через MRO). Backend-класс держит ссылку self._reasoning: Optional[ReasoningStrategy] = None; если задан и kind != plain — работает reasoning-флоу, иначе — обычный one-pass. Одна реализация EmulatedReasoningStrategy применяется ко всем трём backend'ам (HF/vLLM/API) — ветвления на «native» нет, API эмулирует через stop-токены сервера (см. блок выше).

- Один метод: _run_reasoning_then_continuation(self, messages_batch, continuation_fn, generation_config, fmt, enable_thinking, ...) -> (prompts, outputs, infos).
- Параметр continuation_fn(messages_batch, **kwargs) — backend-специфичный калбэк (_generate_batch_impl или _calculate_tokens_proba_batch_impl).
- Reasoning phase: работает с deepcopy generation_config (не мутирует self.generation_config напрямую; текущий prepare_generation_config, model.py:60-79, мутирует self.generation_config с последующим restore — это поведение изменится, см. Risk-блок ниже). Устанавливает eos_token_id=[fmt.end_thinking_token_id], max_new_tokens=max_new_tokens_reasoning, stop_strings=base + [fmt.think_close].
- Стоп-проверка: либо текст оканчивается на fmt.think_close (stopped_by_think), либо generated_len >= max_new_tokens_reasoning и не содержит fmt.think_close в конце (stopped_by_length). Если оба false — Exception (как сейчас, см. _generate_batch_reasoning / _calculate_tokens_proba_batch_reasoning в model.py).
- Continuation phase: создаёт updated_messages с reasoning как assistant-message, зовёт continuation_fn.
- Cleanup: восстановление затронутых полей — через локальный deepcopy оригинала, поэтому try/finally не нужен для глобального состояния self.generation_config (он не трогается).

- Backend-метод generate_batch / calculate_tokens_proba_batch ветвит на self._reasoning_kind. Текущий public `generate_batch` backend'а переименовывается в `_generate_batch_impl` (one-pass реализация); новый `generate_batch` — dispatcher на kind:
```python
def generate_batch(self, messages, *, enable_thinking=False, **kwargs):
    kind = self._reasoning_kind
    if kind == 'plain':
        if enable_thinking:
            self.logger.warning('enable_thinking ignored on plain model (no reasoning support)')
        return self._generate_batch_impl(messages, enable_thinking=False, **kwargs)
    if kind == 'reasoning' and not enable_thinking:
        raise ValueError("model_kind='reasoning' but enable_thinking=False — "
                         "use model_kind='hybrid' or pass enable_thinking=True")
    if not enable_thinking:  # hybrid + False
        return self._generate_batch_impl(messages, enable_thinking=False, **kwargs)
    # hybrid + True, or reasoning + True
    return self._reasoning.run_then_continuation(
        messages, continuation_fn=self._generate_batch_impl, enable_thinking=True, **kwargs,
    )
```
ВАЖНО: дефолт `enable_thinking=False` (а не True) — это сознательное решение для сохранения today's поведения `ApiVLLMModel.generate_batch` / `HFModel.generate_batch` / `VLLMModel.generate_batch` (defolt False в plain-классах, model.py:487,1153,1635). Evaluator всегда передаёт явный `enable_thinking=not args.disable_thinking` (evaluate_model.py:55), так что CLI-прогоны reasoning-моделей продолжают работу. Логгер llmaaj зовёт `model.generate_batch(messages)` без явного флага — дефолт False корректно даёт one-pass (today's поведение llmaaj сохранено). Аналогичный dispatcher для calculate_tokens_proba_batch (через continuation_fn=self._calculate_tokens_proba_batch_impl).

- Auto-detect model_kind в from_pretrained (явный kwarg model_kind= override overrides; в CLI — новая опция `--model_kind {auto,plain,reasoning,hybrid}` с default `auto`):
  1. Вызываем backend-специфичный sniff: HF/VLLM — `self.tokenizer.convert_tokens_to_ids('|THINK_CLOSE|')`; API — HTTP /tokenize (тот же endpoint, что сегодня в ApiVLLMModelReasoning.get_end_thinking_token_id, model.py:710).
  2. Если id != unk_token_id (модель знает think-токен) → default `model_kind='hybrid'`, `self._reasoning_fmt.end_thinking_token_id = id`.
  3. Если id == unk_token_id (модель не знает) → default `model_kind='plain'`, `self._reasoning_fmt = None`.
  4. Явный kwarg `model_kind=` (Python API) или `--model_kind` (CLI) переопределяет auto-detect. `reasoning` НЕ возвращается auto-detect'ом (только `plain` | `hybrid`) — он доступен только через явное указание для пользователей, которые хотят guarantee two-pass и error при попытке отключить thinking. `--model_kind` — единственное расширение argparse в этом рефакторе (см. CLI миграцию).

- Имена подклассов *Reasoning (HFModelReasoning, VLLMModelReasoning, ApiVLLMModelReasoning) УДАЛЯЮТСЯ ПОЛНОСТЬЮ — без deprecated import-alias shims. Все consumers мигрируют на единый backend-класс с `model_kind` kwarg в том же шаге рефактора. Это упрощает код и surface, но требует правки всех импортов в одном заходе (см. CLI миграцию).

4. Название: Логирование семплов — настоящий JSON-массив с потоковой дозаписью
Зачем. Текущий SimpleTaskLogger.log_json (utils.py:64) пишет json.dumps(obj, ensure_ascii=False, indent=4) + '\n' на каждый семпл. Файл <task>.jsonl — конкатенация pretty-printed JSON-объектов без запятых и без обёртки [...]. Не парсится ни как JSON, ни как JSONL; .jsonl расширение вводит в заблуждение. Файлы активно читают глазами (отсюда indent=4), так что просто перейти на компактный NDJSON — не вариант. Хочется: настоящий JSON-массив, pretty-printed, при этом запись по ходу прогона (не «собрать всё в память, записать в конце»).
Описание. Новый llmtf/models/sample_logger.py:
- SampleLogger (ABC) с методами __enter__, __exit__, log_sample(sample, pred, prompt, metric, info), log_json(obj).
- JsonArrayLogger — стратегия по умолчанию для <task>.jsonl:
- __enter__: открыть файл, записать [\n.
- log_sample / log_json: каждый объект пишется с json.dumps(obj, ensure_ascii=False, indent=4). Используется leading-comma стратегия: первый объект пишется без префикса, последующие — с , перед объектом (,\n между объектами). Так при обрыве записи нет «висящей» trailing-запятой.
- __exit__: записать \n]\n, закрыть файл. __exit__ вызывается даже при exception (контекстный менеджер) — массив всегда закрыт.
- _total.jsonl (один агрегированный объект), _params.jsonl и _aggregation_details.jsonl остаются pretty-printed (json.dumps с indent=4) — формат НЕ меняется, файлы должны оставаться читаемыми глазами. Их пишет PrettyJsonLogger (та же ABC, стратегия: json.dumps(obj, ensure_ascii=False, indent=4) + '\n' — эквивалентно текущему SimpleTaskLogger.log_json). Отдельный NdjsonLogger (compact, indent=None) НЕ используется — пользовательские логи обязаны быть pretty.
- В evaluator.py (evaluate_dataset и evaluate_dataset_ppl) заменить SimpleTaskLogger(output_dir, task.run_name()) на JsonArrayLogger(output_dir, task.run_name()) для per-sample; для _total / _params / _aggregation_details использовать PrettyJsonLogger (indent=4, формат тот же что и сегодня — только имя класса меняется, содержимое и читаемость сохраняются).
- utils.py:SimpleTaskLogger удалить после миграции (внешних потребителей в репо нет — grep подтвердит; только evaluator.py использует).
- В AGENTS.md обновить описание per-task выходов: <task>.jsonl теперь валидный JSON-массив объектов (pretty, indent=4); _total.jsonl / _params.jsonl / _aggregation_details.jsonl остаются pretty-printed одиночными объектами (без изменений).
Дизайн на crash-safety: leading-comma → при обрыве в файле [ {sample1} ,\n{sample2} без закрывающего ] — ручное salvaging одной строкой (echo '\n]' >> file). Альтернатива atomic rename (писать в .tmp, в exit — os.rename) — теряет весь прогресс при крэше, неприемлемо для длинных прогонов. Выбран компромисс: progress сохраняется, JSON закрывается всегда через __exit__, при аварийном kill -9 salvaging — одной командой.

Любой внешний (вне репо) consumer этих имён сломается; это сознательное упрощение, задокументированное в AGENTS.md как breaking change этого рефактора.

Risk-блок (regression watch)

- **deepcopy generation_config в ReasoningStrategy (поведенческое изменение).** Текущий `ReasoningModel.prepare_generation_config` (model.py:60-79) мутирует `self.generation_config` напрямую (eos_token_id, max_new_tokens, stop_strings) и восстанавливает его в конце через сохранённый `old_params`. Новый дизайн работает с локальным deepcopy и не трогает `self.generation_config`. Любой внешний код, читающий `self.generation_config` во время reasoning-фазы (логирование, pause/debug, параллельные вызовы в том же процессе), увидит разное. Обязательно: шаг 3 должен сравнить метрики reasoning-модели (Qwen3-think, HF+vLLM) на `enable_thinking=True` и `enable_thinking=False` против baseline до рефактора; расхождение >0.1% — стоп и разбор. Конкретно проверяется absence/presence stop-strings и eos_token_id в момент continuation-генерации.
- **model_kind auto-detect.** Сегодня `evaluate_model.py` всегда инстанцирует `HFModelReasoning`/`VLLMModelReasoning` (даже для instruct/base моделей без think-токена), `enable_thinking=False` рантайм-флаг выбирает one-pass — работает, потому что в one-pass кодpath `end_thinking_token_id` не используется. После миграции авто-detect вернёт `model_kind='plain'` для моделей без think-токена — one-pass behavior идентичен today's (для `enable_thinking=False`), но если пользователь нынче передаст `--enable_thinking` на instruct-модели (today's reasoning-класс не падает, т.к. `_generate_batch_reasoning` идёт через two-pass и `end_thinking_token_id` может быть unk → некорректный eos), то теперь `plain` сделает warning + one-pass fallback — это БОЛЕЕ корректно, но меняет output. Новая валидация бросает ValueError при `model_kind='reasoning'` + `enable_thinking=False`. Семантически правильно, но это breaking-change для пользователей, которые явно выставят `model_kind='reasoning'` и попытаются отключить thinking.
