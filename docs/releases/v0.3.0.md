# LLMTF v0.3.0

Дата выпуска: 20 сентября 2026 года.

`v0.3.0` — крупное обновление архитектуры и runtime-контрактов LLMTF. Версия
поставляется обычным коммитом в ветку `main`; отдельный Python package и Git
tag для этого выпуска не создаются. Программно версия доступна как
`llmtf.__version__`.

Проверенные runtime-образы опубликованы в
[`refalmachine/llmtf`](https://hub.docker.com/r/refalmachine/llmtf):

```bash
docker pull refalmachine/llmtf:v0.3.0-api
docker pull refalmachine/llmtf:v0.3.0-hf-cu129
docker pull refalmachine/llmtf:v0.3.0-vllm-cu129
```

Они предназначены для запуска со смонтированным checkout репозитория и не
содержат отдельную копию исходников.

## Главное

- Единая слоистая архитектура `BaseLLM -> LLM -> Backend` заменила прежнюю
  иерархию model facades и reasoning-подклассов.
- Реализованы независимые `HFBackend`, `VLLMBackend` и `APIBackend` с общей
  orchestration-логикой в `LLM`.
- Reasoning выполняется единым двухфазным механизмом и отделён от sampling
  configuration backend-а.
- Assistant continuation, точный локальный prefill и варианты следующего
  токена централизованы в одном контракте.
- Добавлены строгая схема benchmark YAML, provenance, fingerprinted cache и
  fail-closed обработка частичных backend-ошибок.
- Установка разделена на Docker-профили `api`, `hf` и `vllm` с проверенными
  runtime pins.

## Новая архитектура

Публичная программная сборка модели теперь выглядит так:

```python
from llmtf.backends import VLLMBackend
from llmtf.llm import LLM

backend = VLLMBackend(
    model_context_len=8192,
    gpu_memory_utilization=0.92,
)
model = LLM(backend=backend)
model.from_pretrained(
    "/models/instruct",
    model_kind="plain",
)
```

Reasoning mode выбирается явно через `model_kind`:

- `plain` — всегда one-pass;
- `hybrid` — one-pass с выключенным thinking и two-pass с включённым;
- `reasoning` — обязательный two-pass с явным id закрывающего токена.

Автоматический выбор reasoning/tool parsers не выполняется: эти параметры
зависят от конкретной модели и deployment-а.

## Backend и API

- API-профиль не требует torch, CUDA, Transformers или vLLM.
- `api_profile=auto|openai|vllm` отделяет консервативный OpenAI-compatible
  payload от vLLM-specific extensions.
- API batch сохраняет исходный порядок и завершает задачу ошибкой при
  частичном сбое вместо выдачи неполного результата.
- Request timeout, ограниченные retries, token-counter capability и top-k
  probability scoring имеют явные контракты.
- `--backend_kwargs` принимает JSON object; явные CLI-параметры имеют
  приоритет, неизвестные поля отклоняются до загрузки модели.
- vLLM GPU memory utilization по умолчанию равен `0.92` в offline и managed
  API запусках.

## Prompts и continuation

- Внутренние роли нормализованы к `system`, `user`, `assistant`; историческая
  роль `bot` принимается только на границе task data.
- `predict` содержит только новую генерацию и не включает assistant prefill.
- Локальные HF/vLLM backends сохраняют assistant continuation без скрытого
  trimming.
- Candidate surface forms для probability-задач централизованы; multi-token
  варианты больше не сводятся молча к первому token id.
- Политики `auto`, `exact`, `portable` и `best_effort` делают возможность
  продолжения assistant message явной и записываются в provenance.

## Evaluation, результаты и кеш

- Task failures возвращаются через `EvaluationSummary`; CLI завершается
  ненулевым кодом, если хотя бы одна запрошенная задача не выполнена.
- Sample artifacts записываются как валидный JSON array.
- Params и totals содержат canonical run config и fingerprint. Несовместимый
  кеш больше не принимается как успешный результат.
- Артефакты различают configured/effective reasoning budgets и
  requested/effective thinking mode.
- Контекстный бюджет учитывает backend mode, answer budget и reasoning floor;
  удалённый `max_prompt_len` больше не управляет выполнением.
- PPL остаётся HF-only и означает средний log probability токенов ответа, а не
  экспоненцированную perplexity.

## Benchmark и эксплуатация

- Все YAML runners используют общий строгий loader из `benchmark/config.py`.
- Model kind, thinking mode, reasoning budgets, end token id, API profile,
  backend kwargs и sampling settings передаются единообразно.
- Секреты запрещены в YAML backend kwargs и должны поступать только через
  runtime environment или secret manager.
- Docker-профили используют проверенную линию CUDA 12.9, torch 2.11,
  Transformers 5.9.0 и vLLM 0.21.0.
- API image доказанно работает без torch/vLLM/CUDA; vLLM image расширяет HF
  image, а не дублирует его.

## Breaking changes

- Удалены `llmtf.model`, прежние model facades и все `*Reasoning` subclasses.
  Compatibility aliases намеренно не предоставляются.
- `model_kind=auto` не поддерживается: тип модели задаётся явно.
- Thinking теперь только opt-in через `--enable_thinking`.
- `--max_prompt_len` удалён; используйте `--model_context_len` и task/reasoning
  budgets.
- Старый монолитный `Dockerfile` и `requirements.txt` удалены. Используйте
  `docker/Dockerfile.*` и `requirements/profiles/`.
- Удалены hard-coded launch wrappers и старый single-node runner; используйте
  YAML runners.
- Cache reuse требует совпадения fingerprint. Для намеренно нового запуска
  используйте новый output identity или `--force_recalc`.
- Старые notebooks и закоммиченные example result directories удалены; вместо
  них предоставлены проверяемые исходные примеры в `examples/`.

## Миграция

1. Замените импорт старого model facade на `LLM` и конкретный backend.
2. Укажите `model_kind` явно.
3. Для thinking-enabled запуска передайте model-specific end token id.
4. Удалите `max_prompt_len` из команд и YAML.
5. Не переносите старые totals в новый output без проверки fingerprint.
6. Для foundational модели используйте `--is_foundational` и актуальный
   conversation config.
7. Для OpenAI-compatible endpoint выберите `api_profile`; `vllm` используйте
   только для сервера с соответствующими extensions.

Актуальные команды находятся в корневом

[`docs/configuration.md`](../configuration.md), а готовые малые запуски — в
[`examples/`](../../examples/README.md).

- 57 unit tests, один runtime-тест ожидаемо пропускается на host без

## Известные ограничения

- vLLM 0.21 API удаляет trailing whitespace у некоторых assistant-prefill;
  такие запуски нельзя считать exact local/API parity.
- Foundational stop strings пока не передаются API так же, как локальным
  backend-ам; Base API generation может завершаться позже локальной.
- Native provider reasoning fields и function-calling transport ещё не входят
  в общий response contract.
- PPL не поддерживается vLLM/API.
- Two-pass reasoning поддерживает одну последовательность результата.

Эти и последующие задачи ведутся в
[`BACKLOG.md`](../../BACKLOG.md).
